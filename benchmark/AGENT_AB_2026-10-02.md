# Controlled agent A/B: does injected memory change real agent runs?

Date: 2026-10-02. Status: **null result on a bench with no correctness headroom.** Not evidence for or against
ROI on production work.

## Design (pre-registered before any evaluation run)
- Real LLM runs: one fixed model, one tool set, one prompt shape; 48 evaluation occasions plus 6 baseline runs.
- Codebase: `ledgerkit`, a small payments library with six house gotchas (vendor money units, injectable clock,
  parameterised SQL, path confinement, durable idempotency, error-to-status mapping). 18 tasks, 3 per gotcha.
  Grader: a hidden strict pytest suite run on the agent's `impl.py` in a pristine tree. Before any run, every task
  was validated: the reference solution passes, the naive solution passes the visible tests and fails the hidden ones.
- Arms: CommonTrace's own randomized holdout (`query --experiment`, 50%, per lesson per occasion). The prompt is
  identical across arms; only the work directory's `TASK.md` differs (retrieved lesson text appended or not).
- Store: 6 relevant lessons, 10 unrelated-field distractor lessons.
- Primary contrast (Amendment 2): relevant lesson injected (n=31) vs withheld (n=17).

## Results
| Outcome | Memory | Control | Difference (95% CI) |
|---|---|---|---|
| Hidden-suite pass | 31/31 | 17/17 | 0.0 pts (-11.0 to +18.4), Fisher p=1.0 |
| Total tokens, median | 52,481 | 52,382 | +99 (-1,188 to +770) |
| Duration, median | 8.7 s | 9.0 s | -0.3 s (-2.1 to +0.8) |
| Tool calls, median | 5 | 5 | 0 (-1 to 0) |

- Baseline period (no memory): 6/6 passed. Across all 48 + 6 runs there were zero failures in either arm.
- CommonTrace's own report on the same data: **"Compromised... All 252 recorded occasions succeeded. With no
  variation in the outcome there is nothing for a lesson to move."**
- Static scan (bandit) of all 48 solutions: 0 issues. All SQL-injection and path-traversal checks passed in both arms.

## System-side measurements
- Retrieval latency (warm worker): median 0.34 s, p95 0.40 s, max 0.46 s. First call after start: 6.9 s (model load).
- The relevant lesson was eligible in 48/48 occasions.
- Injected context: median 1,551 characters (about 390 tokens), maximum 3,431.
- **Injection precision was poor: 127 lessons injected across 48 occasions, 31 relevant (24%).** 55 were another
  gotcha's lesson, 41 were unrelated-field distractors. The ranked-eligibility path admits the top-ranked lessons
  regardless of absolute relevance (cross-encoder scores of -7 to -9 were injected). This is a real, fixable
  weakness in the product.
- Per-run total tokens (about 52k) are dominated by the agent harness's own fixed overhead; the injected block is
  under 1% of it, so a token saving of that order cannot be resolved with this design.

## What this shows
1. For a strong current model on a small codebase whose gotchas are documented in the code, memory neither helped
   nor hurt: the model already reads the docstrings. The no-memory arm had no headroom.
2. Memory did not measurably cost tokens or time at this scale (the CI includes about +/-1k tokens).
3. The measurement instrument refused to produce an effect size on a ceiling outcome, which is the behaviour a
   buyer should want.
4. The injection is noisy: three quarters of what an agent receives is irrelevant.

## What this does not show
- Anything about work where the needed knowledge is NOT in the repo (incident history, business rules, past
  decisions). That is the case memory exists for, and it needs a different bench and its own registration.
- Anything about a large codebase, where exploration is expensive and memory could save tokens.
- Production ROI: tasks and lessons were written by the experimenter; one model, one codebase.

## Deviations from the registration (all made before any outcome was seen, hashes in `/tmp/ct_exp`)
- Replications 2 -> 4 per task (runs were cheap). Primary contrast changed to relevant-lesson injected vs withheld
  because the holdout is per lesson. The poisoned-lesson (prompt-injection) arm was dropped: the environment's
  permission policy blocked writing it. The first 16 runs failed with an API rate limit (HTTP 429) and were re-run
  from the stored assignments; excluded as harness failures, not outcomes.
- Lessons were written from documented conventions, because the baseline period produced no failures to learn from.
- The answer bank was compressed and kept outside the agents' work directories, but agents had shell access to the
  machine; per-run tool-call counts of 4-6 are consistent with ordinary work and not with searching the disk.
