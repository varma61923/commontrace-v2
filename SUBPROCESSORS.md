# Subprocessors

This is a factual list of the third parties this codebase actually sends
customer data to, generated by reading `hub/billing.py`, `hub/models.py`,
and `DATA_RETENTION.md` — not a legal document. Audit §2.4 named "no DPA
or subprocessor list" as missing; this closes the *list* half honestly. A
Data Processing Agreement is a contract between two legal entities, and
this repository is neither — that half stays correctly out of scope until
a real company signs one (see `AUDIT_RESPONSE.md` §2.4, §4.4).

## Current subprocessors

| Subprocessor | What it processes | What it never sees |
|---|---|---|
| **Stripe, Inc.** | Payment card details, billing name/email, subscription and invoice history — only for an org that has opted into self-serve billing (`hub/billing.py`). | Trace content, Knowledge Base content, or any org data unrelated to payment. This Hub stores only a Stripe customer id and subscription id (`organizations.stripe_customer_id`/`stripe_subscription_id`) — never a card number, and never routes trace/Knowledge Base data through Stripe in any direction. |

## What determines this list, so it stays current

This list is exactly the set of `httpx`/SDK calls to a third-party host
that exist in `hub/*.py` today. There is exactly one:
`hub/billing.py`'s calls to `api.stripe.com`. If a future change adds
another (an email provider, an object-storage bucket, an LLM API called
server-side), this file is the same list that needs a new row — grep for
outbound HTTP clients in `hub/` to verify there isn't one this list
missed before treating it as current.

## Not on this list, and why

- **An operator's own Postgres.** Not a subprocessor of this codebase —
  it's infrastructure the operator chooses and controls (`hub/DEPLOYMENT.md`
  §2). Whoever hosts it (self-managed, RDS, Cloud SQL, Neon, ...) is the
  operator's own subprocessor relationship to disclose, not one this
  repository can name for them.
- **An operator's own IdP**, if OIDC SSO (`hub/sso.py`) or SCIM
  (`hub/scim.py`) is configured — same reasoning: the operator picks the
  IdP, so the operator's own subprocessor list names it, not this file.
- **A future OpenTelemetry Collector or SIEM** an operator points
  `commontrace/otel_exporter.py`'s spans at — this code exports to
  whatever endpoint the operator configures; it has no opinion on where
  that is, so it names none.

## Who publishes this to a customer

Nobody yet. A subprocessor list is meaningful to a customer only when a
real company stands behind it and keeps it current as part of an actual
DPA — see `AUDIT_RESPONSE.md` §2.4 and §4.4 for what's still a genuine
business decision here, not a repository file.
